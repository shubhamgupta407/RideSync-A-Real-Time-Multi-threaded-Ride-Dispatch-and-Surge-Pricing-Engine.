Decoupled Spatial Dispatch & Multi-Threaded Engine Architecture

RideSync is engineered to overcome traditional bottleneck limitations in high-frequency spatial simulations. By decoupling the visualization layer (Vanilla JS / CSS Mapbox grid) from the core backend logic (C++17 multi-threaded daemon) via an asynchronous HTTP JSON pipeline, RideSync achieves zero-blocking dispatch concurrency, deterministic mutex synchronization, and sub-millisecond Euclidean nearest-neighbor lookups.

01 System Topology & Decoupled Data Pipeline

To prevent UI frame drop during CPU-intensive nearest-neighbor routing and surge pricing calculations, the frontend dashboard acts as a stateless spatial viewer that polls state snapshots from the C++17 HTTP server at a configurable rate (default 1000ms).

02 Multithreaded Concurrency & Thread Synchronization Sequence

RideSync models real-world dispatch concurrency by running autonomous worker threads for riders, drivers, and the central dispatch engine. Thread safety and race-condition elimination are guaranteed using standard C++17 synchronization primitives.

Figure 2.1 — Concurrency Sequence & Mutex Lock Timeline

🔒 Mutex Lock Contention Elimination

To prevent background driver simulation threads from freezing the REST API endpoint during state polling, RideSync enforces minimal critical section scopes. The driver_mutex is held strictly during coordinate assignment and O(N) spatial scans, ensuring 0% deadlock probability under high concurrency.

🧵 Detached Worker Threading Architecture

When a driver is assigned to a ride request, the dispatch engine spawns a lightweight detached std::thread that handles step-by-step physical coordinate movement across the city grid. Once the 9000ms trip concludes, the worker safely restores the vehicle to AVAILABLE status.

03 Dynamic Surge Pricing State Machine & Heatmap Matrix

RideSync dynamically evaluates local zone density across the city grid in real time. The city is partitioned into discrete zones where supply ($S$, available drivers) and demand ($D$, pending ride requests) govern automatic fare multiplier transitions.

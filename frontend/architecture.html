System Architecture & Data Flow

An overview of RideSync's decoupled design, thread synchronization, and surge pricing logic. The visualization layer runs independently from the C++17 dispatch engine to ensure zero-blocking concurrency.

1. System Topology

Stateless Frontend The UI polls /state every second over HTTP. Zero CPU-heavy routing occurs in the browser.
C++17 HTTP Server Built with lightweight cpp-httplib and header-only JSON serialization for fast request handling.
Mutex Protected State Shared driver lists and request queues use std::lock_guard to prevent data races during API reads.

2. Thread Concurrency Sequence

Condition Variables Instead of busy-waiting, the dispatcher thread sleeps using cv.wait() and wakes instantly when a request arrives.
Euclidean Matchmaking The background thread scans active vehicles inside a mutex lock to find the nearest candidate in O(N) time.
Detached Trip Workers Assigned vehicles run on autonomous worker threads to simulate physical grid navigation without blocking new dispatches.

3. Dynamic Surge State Machine

Real-Time Density Evaluation Each zone continuously monitors the delta between pending ride requests (Demand) and idle vehicles (Supply).
Visual Heatmap Feedback Surge zones emit glowing radial gradients on the map (yellow for 1.5x, red for 2.0x) to guide drivers toward high-demand areas.
Self-Balancing Supply As vehicles complete trips or enter high-surge zones, supply increases, automatically normalizing the tier back to 1.0x.
